# OS Update Channel And Fleet Spec

Genome's Agentic OS needs an update model for many installed customer OS roots.
The update system must support "phone home" visibility and automatic updates
without leaking customer data or silently overwriting local/operator changes.

## Goals

- Track installed OS roots across operator and customer environments.
- Check for available updates from a canonical source.
- Apply safe additive updates automatically when policy allows.
- Require approval for risky, destructive, or customer-visible migrations.
- Maintain rollback state.
- Keep customer data and project contents out of telemetry.
- Make update status visible to operators and agents.

## Non-Goals

- No silent exfiltration of prompts, customer docs, source code, or secrets.
- No unmanaged remote command execution.
- No destructive auto-update by default.
- No dependency on Notion as the only update control plane.

## Installed Files

```text
~/agentic_os/
  .agentic_root
  agentic-os.package.json
  agentic-os.lock.json
  agentic-os.local.json
  UPDATE_POLICY.md
  registries/
    updates.yml
    capabilities.yml
```

Customer installs use the same files, with customer-specific policy values.

## Update Identity

Each installed OS root gets an installation identity:

```yaml
install_id: 01HY...
os_name: genomes-agentic-os
channel: stable
installed_version: 0.1.0
customer_id: optional-customer-safe-id
environment: operator | customer
created_at: 2026-05-23T00:00:00Z
```

The install id should be random and non-secret. It identifies an installed OS
root, not a person or customer source repository.

## Update Channels

| Channel | Purpose | Auto-Update Default |
| --- | --- | --- |
| `dev` | local operator dogfooding | manual |
| `preview` | early operator/customer pilots | check automatically, apply manually |
| `stable` | normal customer installs | safe additive updates may auto-apply |
| `pinned` | regulated or frozen installs | no auto-apply |

## Phone Home Contract

Phone home should send only operational metadata:

```json
{
  "install_id": "01HY...",
  "os_name": "genomes-agentic-os",
  "installed_version": "0.1.0",
  "channel": "stable",
  "capability_hash": "sha256:...",
  "last_update_check": "2026-05-23T00:00:00Z",
  "doctor_summary": {
    "ok": true,
    "blockers": 0,
    "warnings": 2
  }
}
```

Do not send:

- prompts
- customer documents
- source code
- env var values
- MCP tokens
- raw logs
- project names unless explicitly customer-approved

## Update Manifest

The update server or source repo publishes an update manifest:

```json
{
  "schema_version": 1,
  "os_name": "genomes-agentic-os",
  "version": "0.2.0",
  "channel": "stable",
  "released_at": "2026-05-23T00:00:00Z",
  "minimum_supported_version": "0.1.0",
  "packages": [
    {
      "id": "context-mode",
      "version": "1.2.0",
      "type": "mcp",
      "update_policy": "additive_non_destructive"
    }
  ],
  "migrations": [
    {
      "id": "add-visible-capability-registries",
      "risk": "safe_additive",
      "requires_approval": false
    }
  ],
  "checksums": {},
  "signature": "optional-signature"
}
```

## Update Policies

| Policy | Behavior |
| --- | --- |
| `manual_only` | Check and report only. Never apply automatically. |
| `safe_additive` | Auto-apply files that do not overwrite local edits. |
| `prompt_before_apply` | Download and plan, then require operator approval. |
| `pinned_version` | Reject updates unless explicitly unpinned. |

Default:

- Operator OS root: `prompt_before_apply`.
- Customer OS root: `safe_additive` for templates/registries/docs, approval for
  hooks, MCPs, rules, and executable changes.

## Apply Flow

1. Read local `agentic-os.lock.json`.
2. Check update manifest for the configured channel.
3. Compare package versions and registry hashes.
4. Generate an update plan.
5. Run preflight doctor checks.
6. Create rollback snapshot for files that may change.
7. Apply safe additive changes.
8. Block on approval for risky changes.
9. Run post-update doctor checks.
10. Write lockfile and update registry.
11. Emit update result to local logs and optional control plane.

## Rollback

Each update writes:

```text
06-runs-and-logs/updates/<timestamp>/
  update-plan.json
  changed-files.txt
  rollback/
  doctor-before.json
  doctor-after.json
```

Rollback must restore generated files changed by the update. It must not delete
operator-created work unless that file was explicitly generated by the update
and recorded in the rollback snapshot.

## Control Plane Options

The update channel can be backed by:

- Git release manifest in the source package repo.
- Static HTTPS manifest.
- Notion database for operator visibility only.
- Future hosted update service for customer fleet status.

Notion should not be the only source of truth. It can mirror status and provide
operator-friendly dashboards.

## CLI Surface

```text
agentic-os update check --root ~/agentic_os
agentic-os update plan --root ~/agentic_os
agentic-os update apply --root ~/agentic_os
agentic-os update rollback --root ~/agentic_os --run <id>
agentic-os update status --root ~/agentic_os
```

Automation surface:

```text
agentic-os update heartbeat --root ~/agentic_os
```

The heartbeat may phone home and write status, but it must not apply risky
updates without policy approval.

## Customer Safety Rules

- Customer installs must declare their update channel and policy in
  `UPDATE_POLICY.md`.
- Auto-update must be disableable.
- Executable updates, hook changes, MCP changes, and permission changes require
  either explicit customer policy or operator approval.
- Telemetry must be summarized and redacted by design.
- Every update must be inspectable after the fact.

## Doctor Checks

`agentic-os doctor` should include:

- installed version
- update channel
- last update check
- pending updates
- last successful update
- failed update attempts
- rollback availability
- phone-home status
- telemetry policy status

## Open Decisions

- Whether update manifests are signed in V1 or only checksum-verified.
- Whether phone-home endpoint is a static HTTP collector, a hosted API, or a
  GitHub/Notion-backed bootstrap.
- Whether customer installs should default to `stable` or `pinned`.
- Whether operator-managed customer fleets should group installs by customer,
  environment, or capability bundle.
