# Harness Context Contract

Genome's Agentic OS should use `config.toml` and visible context files together.
`config.toml` makes the harness start, discover, and load correctly. Markdown
files define portable operating behavior that Codex, Claude, humans, and future
harnesses can all inspect.

The goal is to avoid duplicating instructions across harness-specific files
while still giving each layer of the OS enough local routing, rules, and tool
visibility.

## Contract Summary

Every installed OS root and routeable layer should use this base file set:

```text
.agentic_root
AGENTS.md
CLAUDE.md
ROUTER.md
CONTEXT.md
RULES.md
TOOLS.md
```

`AGENT.md` should not be generated by default. It is only allowed as a
compatibility adapter if a future harness proves it needs that exact filename.

## File Responsibilities

| File | Responsibility |
| --- | --- |
| `.agentic_root` | Marks the installed OS root and lets harness config detect the OS boundary. |
| `AGENTS.md` | Harness-neutral entrypoint. Tells every agent to read the local context files, route before acting, and repeat after changing directories. |
| `CLAUDE.md` | Claude-only adapter. Should include `AGENTS.md` instead of duplicating instructions. |
| `ROUTER.md` | Decides where the current request belongs next. Returns a target directory, workflow, automation, project, or stop condition. |
| `CONTEXT.md` | Explains what this layer is, what systems it represents, and what good output means here. |
| `RULES.md` | Holds constraints, approvals, safety boundaries, coding rules, and local operating rules. |
| `TOOLS.md` | Lists available skills, commands, MCPs, plugins, wrappers, registries, and when to use them at this layer. |

Claude's adapter should be intentionally small:

```md
@AGENTS.md
```

## Agent Routing Loop

Agents should always start from the installed OS root, where `.agentic_root`
lives. The root context decides the first route. The selected route may provide a
narrower route.

Required loop:

```text
1. Start at the installed OS root.
2. Read AGENTS.md.
3. Read ROUTER.md, CONTEXT.md, RULES.md, and TOOLS.md in the current directory.
4. Classify the user request against ROUTER.md.
5. If ROUTER.md points to a narrower directory, cd there.
6. Repeat steps 3-5 until no narrower route applies.
7. Act only after loading the final layer's context files.
8. Record routing gaps or missing tools in the run log or closeout artifact.
```

Example:

```text
User request:
  /pull-request for this PR <github-link>

~/agentic_os/ROUTER.md:
  github-link -> los/

~/agentic_os/los/ROUTER.md:
  github-link -> 02-projects/<projectname>/

Final working directory:
  ~/agentic_os/los/02-projects/<projectname>/
```

The final layer's `TOOLS.md` can point to local or inherited tools:

```text
TOOLS.md
  skills:
    - /pull-request
    - /orchestrate
  skill_paths:
    - .codex/skills/
    - ../../../skills/
    - ~/agentic_os/skills/
  mcp:
    - github
    - atlassian
    - losmon-memory
```

The visible registry is authoritative even when a harness requires additional
hidden installation paths. If Codex or Claude needs copied/symlinked runtime
skills, the installer should generate those from `TOOLS.md` and the capability
registries.

## `config.toml` Responsibilities

Codex `config.toml` should bootstrap discovery and execution behavior. It should
not become the main place for business rules, routing tables, or long prompt
instructions.

Use `config.toml` for:

- OS root detection with `.agentic_root`.
- Project/root marker configuration.
- Default model and reasoning profiles.
- Sandbox and approval defaults.
- MCP server declarations.
- Tool and skill search paths.
- Subagent limits and orchestration defaults.
- Harness-specific config that cannot live in portable markdown.
- Pointers to the context-file contract.

Do not use `config.toml` for:

- Large business-context prose.
- Domain routing tables.
- Customer-specific operating rules.
- Long duplicated copies of `AGENTS.md`, `ROUTER.md`, `CONTEXT.md`, `RULES.md`,
  or `TOOLS.md`.
- Secrets.

## Context File Precedence

When multiple layers apply, narrower context wins unless the broader layer is a
safety rule.

Precedence:

1. Active user instruction.
2. Final routed layer's `RULES.md`.
3. Parent layer `RULES.md`, with strictest safety rule winning.
4. Final routed layer's `ROUTER.md`, `CONTEXT.md`, and `TOOLS.md`.
5. Parent context files.
6. Harness config defaults.

Routing uses the narrowest applicable router. Safety uses the strictest
applicable rule.

## Tool Discovery

`TOOLS.md` is the human- and agent-readable tool surface. It should be generated
or validated from the visible capability registry.

Recommended sections:

```md
# Tools

## Skills

## Commands

## MCP Servers

## Plugins And Libraries

## Local Wrappers

## When To Use What

## Missing Or Disabled
```

Harness-specific folders such as `.codex/skills/` may exist under a routeable
layer, but they are implementation details. The OS should expose the intended
tools in `TOOLS.md` and let the installer/config layer make the harness match.

## Installer Implications

Fresh installs should:

- Create `AGENTS.md`, `CLAUDE.md`, `ROUTER.md`, `CONTEXT.md`, `RULES.md`, and
  `TOOLS.md` at the root.
- Create `ROUTER.md`, `CONTEXT.md`, `RULES.md`, and `TOOLS.md` in routeable
  domain/project/workflow layers where useful.
- Stop creating `AGENT.md` by default.
- Render `CLAUDE.md` as an include adapter.
- Generate Codex config with `.agentic_root` in root markers.
- Configure Codex skill/tool paths from visible registry state.
- Validate that every routeable layer has a router and either local or inherited
  context/rules/tools.

## Validation

`agentic-os validate` should detect:

- Missing `.agentic_root` at the installed root.
- Missing root `AGENTS.md`, `CLAUDE.md`, `ROUTER.md`, `CONTEXT.md`, `RULES.md`,
  or `TOOLS.md`.
- `CLAUDE.md` duplicating large instruction bodies instead of including
  `AGENTS.md`.
- Unexpected generated `AGENT.md` files unless compatibility mode is enabled.
- Routeable layers with `ROUTER.md` but no `CONTEXT.md`, `RULES.md`, or
  `TOOLS.md` inheritance.
- Tool entries in `TOOLS.md` that are not present in the capability registry or
  harness install path.

## Open Decisions

- `BRAIN.md` is retired from generated layer defaults. Shared bootstrap behavior
  belongs in `AGENTS.md`.
- Whether project-level `.codex/skills/` folders should be generated, symlinked,
  or only referenced from `TOOLS.md`.
- Whether `RULES.md` should be split into safety, style, and approval files for
  large customer installs.
- How much of `TOOLS.md` should be hand-authored versus generated from
  registries.
