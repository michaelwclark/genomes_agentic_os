# Contributing

## Install the commit hooks

Commit messages in this repository follow
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Install
the hook once per clone:

```bash
uv sync
uv run pre-commit install --hook-type commit-msg
```

The hook rejects a malformed message before the commit is written:

```
$ git commit -m "fixed the thing"
commit-msg...............................................................Failed
commit validation: failed!
please enter a commit message in the commitizen format.
```

A conforming message passes:

```
$ git commit -m "fix(runtime): keep the approval state materialized"
commit-msg...............................................................Passed
```

`git commit` with no `-m` opens your editor as usual. If you would rather be
prompted for each field, `uv run cz commit` builds the message interactively.

### If `pre-commit install` refuses

```
[ERROR] Cowardly refusing to install hooks with `core.hooksPath` set.
```

Some clones carry a redundant `core.hooksPath` that points at the very
directory git would use anyway. It does nothing except block the installer.
Confirm that is the case and clear it:

```bash
git config --show-origin --get core.hooksPath   # expect .../.git/hooks
git config --unset core.hooksPath
```

Only unset it once you have confirmed the value is the repository's own
`.git/hooks`. If it points somewhere else, the clone is deliberately using a
different hooks directory and you should install into that instead.

### Worktrees share one hooks directory

This repository is commonly worked through many git worktrees. They all share
`.git/hooks`, so installing the hook once covers every worktree, and
uninstalling it in one removes it everywhere. That is also why only the
`commit-msg` stage is configured — a shared hook that rewrote or rejected file
contents would disrupt work in unrelated worktrees.

## Allowed commit types

`build`, `bump`, `chore`, `ci`, `docs`, `feat`, `fix`, `perf`, `refactor`,
`revert`, `style`, `test`. Note that `release` is **not** a type; use `chore` or
`ci` for release plumbing.

Format:

```
<type>[optional scope]: <description>

[optional body]

[optional footer]
```

Breaking changes take a `!` after the type/scope (`feat(cli)!: ...`) or a
`BREAKING CHANGE:` footer.

Merge commits are exempt, as are messages beginning `Revert`, `Pull request`,
`fixup!`, or `squash!`.

## Versioning

`[project] version` in `pyproject.toml` is the single source of the release
version. Commitizen derives the next version from the commits since the last
tag and writes it back there:

```bash
uv run cz bump --dry-run     # show the version this would produce
```

Tags are `v$version`, matching the equality check the Release workflow performs
against `pyproject.toml`. The project is deliberately held below 1.0
(`major_version_zero`), so a breaking change bumps the minor rather than the
major version.

`CHANGELOG.md` is hand-curated in
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format and is not
generated by `cz bump`.

## Before you open a pull request

```bash
uv run pytest
```

On the pull request, `Commit messages` re-checks every commit server-side (the
local hook can be bypassed with `--no-verify`; this check cannot), and
`Python suite and packaging` runs the full test suite and validates the wheel
and source distribution.
