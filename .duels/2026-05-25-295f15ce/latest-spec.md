# Capability Registry v3

## Vision

Genome's Agentic OS must make every installed capability — commands, skills, MCP servers, plugins, libraries, hooks, rules — discoverable from a single visible root, with one normalized record shape, and with harness-specific dot-folders (`.codex/`, `.claude/`) generated deterministically from that root. The registries are the composition surface; the dot-folders are adapters. Operator memory and tribal knowledge stop being load-bearing.

**Non-goals**: replacing Codex/Claude runtimes, packaging third-party MCPs as our own, or building a generic plugin marketplace. v1 only standardizes how the OS describes what *is* installed and refuses to consider unregistered code as installed.

## Architecture

### Installed Root

```
~/agentic_os/
  .agentic_root                   # marker file, contains schema_version
  INVENTORY.md                    # generated, read-only header asserts so
  agentic-os.package.json         # declared capabilities, hand-edited
  agentic-os.lock.json            # generated, content-addressed
  agentic-os.local.json           # per-host overrides, gitignored
  .agentic-os.staging/            # staging tree for adapter promotion, gitignored
  bin/  commands/  skills/  mcp/  plugins/  libraries/  hooks/  rules/
  registries/
    capabilities.yml              # generated from per-type registries
    commands.yml  skills.yml  mcp.yml  plugins.yml
    libraries.yml hooks.yml  rules.yml
  projects -> ~/projects          # symlink
  shared_factory/  personal/  clarks_consulting/  los/  archive/
```

Dot folders (`.codex/`, `.claude/`) are generated outputs. Header on every generated file: `# GENERATED by agentic-os installer — do not edit by hand. Source: registries/<file>.yml`. Generated adapters additionally carry a `# AGENTIC-OS-GENERATION: <hash>` line (see Promotion phase below).

### Capability Records: declared vs normalized (two schemas, one base)

Per-type registry files are **declared** records (hand-edited). `capabilities.yml` and lock entries are **normalized** records (generated). Both share a base.

**Base** (`schemas/capability-base.schema.json`) — fields every record carries:

```yaml
id: context-mode                   # globally unique, kebab-case, [a-z0-9-]+
type: command|skill|mcp|plugin|library|hook|rule
display_name: Context Mode
visibility: operator|customer
customer_safe: false               # required boolean, no default
source:
  package: context-mode
  registry: registries/mcp.yml
update:
  policy: additive_non_destructive|replace|pinned
```

**Declared** (`schemas/capability-declared.schema.json`) — what per-type registries must conform to. Extends base with:
- `status` — optional, allowed values: `declared` (default if omitted) or `disabled` (skip during install). Hand-editable.
- Per-type required fields per the table below.
- **Forbids**: `source.content_hash`, derived statuses (`installed`, `broken`), and the entire `doctor` object. Hand-maintaining generated values is a schema violation.

**Normalized** (`schemas/capability-normalized.schema.json`) — what `capabilities.yml` and lock entries must conform to. Extends base with:
- `status` — required, one of `installed | broken | declared | disabled` (derived; see lifecycle below).
- Per-type required fields per the table below.
- A `status`-branched `oneOf` that resolves the disabled-record invariant. **The encoding operates on the actual nested object structure** — JSON Schema `required` matches literal property names at the current depth only and does NOT interpret dotted paths. The correct, implementer-binding encoding is:

```yaml
oneOf:
  - if:
      properties: { status: { const: "disabled" } }
    then:
      # disabled records: source must NOT have content_hash; doctor object must be ABSENT entirely
      properties:
        source:
          not: { required: ["content_hash"] }
      not: { required: ["doctor"] }
  - if:
      properties: { status: { enum: ["installed", "broken", "declared"] } }
    then:
      # non-disabled records: source.content_hash AND doctor.last_run_status BOTH required
      required: ["doctor"]
      properties:
        source:
          required: ["content_hash"]
        doctor:
          type: object
          required: ["last_run_status"]
          properties:
            last_run_status:
              enum: ["pass", "fail", "not_run"]
```

A top-level `{ not: { required: ["doctor.last_run_status"] } }` is INCORRECT — JSON Schema would treat `"doctor.last_run_status"` as a single literal property name at the root object level and the constraint would fail open. Implementers MUST use the nested form above. AC13's positive and counter-fixtures both target the nested encoding and would fail if the wrong dotted form were used.

Disabled records appear in `capabilities.yml`, `agentic-os.lock.json`, and `INVENTORY.md` (annotated `(disabled)`) so operators can see what was declared but turned off; they never appear in harness adapter outputs and their content is never copied into `install.target`.

**Per-type required field table** — applies to both schemas:

| type | install.target | install.command | provides.tools | requires.commands | harness_targets |
|---|---|---|---|---|---|
| mcp | required | required | required (≥1) | required (≥1) | required (≥1 target) |
| command | required | optional | forbidden | optional | required |
| skill | required | forbidden | forbidden | optional | required |
| plugin | required | forbidden | optional | optional | required |
| library | required | forbidden | forbidden | optional | forbidden |
| hook | required | required | forbidden | optional | optional |
| rule | required | forbidden | forbidden | forbidden | required |

Per-type enforcement uses JSON Schema `if/then/else` keyed on `type`. Exact field-presence rules:
- **`required`**: the property MUST be present. For maps/lists, the value MUST also be non-empty when the table appends `(≥1)`; otherwise a present-but-empty container is allowed.
- **`optional`**: the property MAY be absent OR present (empty or non-empty).
- **`forbidden`**: the property MUST be absent. Present-but-empty (e.g., `provides.tools: []`) FAILS validation. Encoded as `{ not: { required: [<field>] } }` on the parent object inside the matching `if` branch.

Examples: a `type: rule` record omitting `install.command`, `provides.tools`, and `requires.commands` validates; the same record with `provides.tools: []` (present-but-empty) FAILS. A `type: mcp` record omitting `provides.tools` fails.

### Status lifecycle (operator intent vs derived state)

Per-type registry files are **read-only inputs**. The installer never writes back to them. `status` in declared records reflects operator intent only (`declared` | `disabled`).

`status` in normalized records is derived deterministically by the installer:
- `disabled` — operator marked `disabled` in the declared record; install pipeline short-circuits for that record. Its normalized form OMITS `source.content_hash` AND the entire `doctor` object (enforced by the schema's `status: disabled` branch).
- `declared` — transient state after step 4 and before step 5 (visible only during interrupted runs or `--dry-run` partial executions).
- `broken` — install copy + normalization succeeded, but doctor checks failed for the record.
- `installed` — install copy + normalization succeeded and every doctor check passed.

AC6 is implementable because `broken` is a derived value, computed once per install run from doctor output. The per-type registry file is not mutated; only `capabilities.yml`, `agentic-os.lock.json`, and adapter outputs reflect the derived status.

### Registries as composition surface

The per-type registry files are the only place where capabilities are declared. `capabilities.yml` and `INVENTORY.md` are generated from them in a single deterministic pass. The build is pure: same inputs → byte-identical outputs (sorted by `id`, fixed YAML emitter settings, fixed Markdown template). CI asserts this by running `install --dry-run` twice into separate output dirs and `diff -r`-ing them.

Generated artifacts that fall out of sync with their sources cause `agentic-os doctor` to exit non-zero.

### Harness adapter generation (single-emission, per-file atomic promotion + recovery)

Harness-specific config files are generated by deterministic emitters, one per harness:

- `emit_codex_config(normalized_caps, generation_id) -> .codex/config.toml`
- `emit_claude_docs(normalized_caps, generation_id) -> CLAUDE.md`
- `emit_agents_md(normalized_caps, generation_id) -> AGENTS.md`

Emitters run **exactly once per install**, after doctor has resolved final `installed`/`broken` status. Output writes follow a stage-then-promote pattern.

**Atomicity model (honest):**
- Each individual file promotion is atomic on POSIX (`os.replace` is a single inode swap — observers see either the prior file or the new file, never a torn intermediate).
- The cross-file promotion of three adapters is NOT a single atomic transaction. A crash between two `os.replace` calls can leave a mixed-generation adapter set: `.codex/config.toml` carries the new generation while `CLAUDE.md` and `AGENTS.md` still carry the prior generation.
- The spec accepts mixed-generation as a recoverable transient state, not an unreachable one, and provides explicit detection + recovery.

**Generation marker.** Each staged adapter is emitted with a single mandatory line near its top (after the `# GENERATED` banner):

```
# AGENTIC-OS-GENERATION: <generation_id>
```

where `generation_id` equals the new install's `manifest_hash` (the same hash that will land in `agentic-os.lock.json`). After promotion, every live adapter carries this line. **Doctor's `mixed-generation` check reads the `AGENTIC-OS-GENERATION` line from each live adapter and asserts every value equals the current lock's `manifest_hash`.** Any mismatch is a FAIL.

**Recovery.** `agentic-os install --resume-promotion`:
- If `.agentic-os.staging/` still contains all expected staged adapters AND each staged adapter's `AGENTIC-OS-GENERATION` line matches the current lock's `manifest_hash` (the resume target): re-run step 8 from the existing staged tree.
- Otherwise: re-run the install pipeline from step 6 (regenerate staging, then promote).
- The resume command is idempotent — running it twice produces the same final live-adapter set.

If the process crashes or exits non-zero anywhere from step 1 through step 7, live adapter files are byte-identical to their pre-install state. The staging tree may be left behind; `agentic-os doctor --fix` or the next install's startup phase cleans it up.

The Claude/Agents emitters use a sentinel pattern: a hand-curated header above `<!-- AGENTIC-OS:REGISTRY-CURATED BELOW -->` is read from the live file BEFORE the staged write and preserved verbatim; everything below is regenerated (and the `AGENTIC-OS-GENERATION` line lives inside the regenerated portion, just below the sentinel). If the sentinel is missing in the live file, the emitter aborts before any staged write.

Emitters consume normalized records only; records with `status != installed` (declared, broken, disabled) are excluded from adapter outputs.

### Install contract (enforced steps)

1. Parse `agentic-os.package.json`; schema-validate.
2. Schema-validate every per-type registry file against `capability-declared.schema.json` (per-type required fields enforced via `if/then/else` discriminator on `type`). Abort on any violation with a file:line pointer. This step runs against hand-authored content only and does NOT require `source.content_hash`.
3. For each declared record with `status != disabled`: resolve source, compute `content_hash`, copy/link to its `install.target`. Disabled declared records are skipped entirely — no source resolution, no hash computation, no file copy.
4. Normalize: emit one normalized record per declared record. For non-disabled records, inject `content_hash` (from step 3), `status: declared`, and a `doctor` object with `last_run_status: not_run`. For disabled records, pass through with `status: disabled` and OMIT both `source.content_hash` and the entire `doctor` object (matches the normalized schema's `status: disabled` branch).
5. Run doctor checks against every non-disabled normalized record. PASS → `status = installed`, `doctor.last_run_status = pass`; FAIL → `status = broken`, `doctor.last_run_status = fail` with `message`. Disabled records are not doctored.
6. Compute `generation_id` = `manifest_hash` over the sorted final normalized entries. Render harness adapters into the staging tree `<install_root>/.agentic-os.staging/` — one staged path per live adapter. Each staged adapter includes the `# AGENTIC-OS-GENERATION: <generation_id>` line. Records with `status != installed` (declared, broken, disabled) are excluded. **No live adapter files are touched.**
7. Schema-validate the final normalized set against `capability-normalized.schema.json`. The schema's `status`-branched `oneOf` enforces (a) disabled records omit `source.content_hash` AND the `doctor` object, AND (b) non-disabled records have BOTH `source.content_hash` AND `doctor.last_run_status`. Abort on any violation with a pointer.
8. **Promotion phase** (per-file atomic, with cross-file recovery via generation marker):
   a. For each adapter in the deterministic order `.codex/config.toml`, `CLAUDE.md`, `AGENTS.md`: `os.replace` the staged file to its live path. Each replace is per-file atomic.
   b. After all three adapter promotions return success, write `agentic-os.lock.json` containing `{id, content_hash?, install_target, status, doctor.last_run_status?}` per capability — `content_hash` and `doctor.last_run_status` are absent for disabled records — plus a top-level `manifest_hash` equal to `generation_id`. **The lock write is the commit point.**
   c. Write `capabilities.yml` and `INVENTORY.md`.
   d. Delete `.agentic-os.staging/`.

Crash semantics:
- Crash from step 1 through step 7 → live adapters byte-identical to pre-install (no `os.replace` has run yet); staging tree may remain.
- Crash mid-8a (between two `os.replace` calls) → mixed generation: some live adapters carry the new `generation_id`, others carry the prior. Lock still reflects the prior `manifest_hash`. `agentic-os doctor` detects via `mixed-generation` check.
- Crash between 8a (complete) and 8b → all three live adapters carry the new `generation_id`, but the lock still reflects the prior `manifest_hash`. `agentic-os doctor` detects via `mixed-generation` check (live adapters disagree with lock).
- Crash between 8b and 8c → lock and adapters agree; `capabilities.yml`/`INVENTORY.md` reflect the prior generation. Doctor flags `inventory-stale` (lower severity than `mixed-generation`).

Recovery from any of these is `agentic-os install --resume-promotion`. File copies from step 3 are content-addressed and idempotent on re-run.

`--dry-run` mode runs the identical pipeline with one change: every write — file copies in step 3, staged adapters in step 6, the promotion targets in step 8a, and the artifact writes in 8b/8c — is redirected to an output tree at `./agentic-os.out/dry-run/` (override with `$AGENTIC_OS_DRYRUN_DIR`). The real tree (`~/agentic_os/`) is not mutated. Doctor checks in step 5 execute against the dry-run target tree, so `mcp-starts` and `command-resolves` exercise the real artifacts just written into the dry-run dir. AC3 and AC7 tests run `install --dry-run` twice into separate output dirs and `diff -r` them.

### Secret protection (defense in depth)

Three independent gates, all required; failure of any one fails the build/install.

1. **Schema-level structural rules** (runs at step 2):
   - `requires.env` is `array<string>`, each string matching `^[A-Z][A-Z0-9_]*$` — env var names only, no `=`, no values.
   - `install.args` is `array<string>`, no element may match `://[^/]+:[^/]+@` (credential-bearing URL).
   - Any string scalar longer than 256 chars fails (no embedded blobs in registry files).

2. **Regex grep gate** (CI, runs over `registries/**/*.yml`):
   - `(?i)(api[_-]?key|token|secret|password|passwd|bearer|aws_[a-z]+_key|private_key)\s*[:=]\s*['"]?[A-Za-z0-9+/=_-]{8,}`

3. **Entropy gate** (CI, runs over `registries/**/*.yml`):
   - For any string scalar over 20 chars, compute Shannon entropy; fail if > 4.5 bits/char AND the surrounding key path is not on the allowlist (`source.package`, `display_name`, `description`, `doctor.last_run_status.message`, `source.content_hash`).

The three gates compose: structural rules catch obvious shape errors at schema validation; the regex gate catches named credentials; the entropy gate catches unlabeled blobs (random tokens dropped into list values, command args, URLs).

## Phases

### P1 — Registry primitive + INVENTORY (weeks 1–2, hard cap 2 weeks)

- Ship `capability-base.schema.json`, `capability-declared.schema.json`, `capability-normalized.schema.json` (including the `status`-branched `oneOf` with the nested `not: required` encoding for disabled records) and a validator library wrapping both.
- Ship per-type registry files as declared records (no `content_hash`, `status` omitted or `declared`/`disabled`) for the current installed set: `make-skill`, `make-domain`, `make-automation`, `make-workflow`, `orchestrate`, `os-doctor`, `os-update`, `os-inventory`; skills currently in `shared_factory/05-knowledge/skills/`; MCPs `context-mode`, unified memory (MemPalace+CoCoIndex), Notion, GitHub, Atlassian.
- `agentic-os install --dry-run` produces a deterministic output tree under `./agentic-os.out/dry-run/`.
- `agentic-os doctor` runs minimum checks: declared-schema validity of per-type registries, normalized-schema validity of generated artifacts (including the disabled-branch invariants), generated artifacts in sync (re-run dry-run, diff), command paths resolve, MCP `command` exists on PATH.
- CI runs the three-gate secret protection on every PR.
- Exit P1 when: doctor exits 0 on a fresh install of the current OS contents; INVENTORY.md is hand-reviewed; CI runs the full pipeline on every PR.

### P2 — Harness adapter generation (weeks 3–4, hard cap 2 weeks)

- Implement `emit_codex_config`, `emit_claude_docs`, `emit_agents_md` with sentinel-preserving writes into the staging tree, each emitting the `# AGENTIC-OS-GENERATION: <generation_id>` marker line.
- Wire emitters into the install flow (step 6) and the per-file atomic promotion phase (step 8).
- Lock-file generation as commit point (step 8b).
- Implement `agentic-os install --resume-promotion` recovery flow.
- Implement the test-only `AGENTIC_OS_FAULT_AFTER_STEP=<n>` env hook (used by AC14) AND `AGENTIC_OS_FAULT_AFTER_REPLACE=<adapter_name>` env hook (used by AC14 mid-promotion fault).
- Doctor adds: sentinel-present check, generated dot-files match emitter output (re-emit into dry-run tree, diff), staging-tree cleanup, `mixed-generation` check comparing each live adapter's `AGENTIC-OS-GENERATION` line against the lock's `manifest_hash`, `inventory-stale` check.
- Exit P2 when: a clean install regenerates `.codex/config.toml`, `CLAUDE.md`, `AGENTS.md` deterministically; re-running `install --dry-run` on an unchanged tree produces a zero-byte diff; hand-curated headers above sentinels survive a round-trip; AC14 (a), (b), and (c) all pass.

### P3 — Customer-safety gating + update policy (weeks 5–6, hard cap 2 weeks)

- Enforce `customer_safe` at install time: a customer-mode install (`AGENTIC_OS_PROFILE=customer`) refuses any capability with `customer_safe: false`, exits non-zero, lists offenders.
- Enforce `update.policy`: `additive_non_destructive` updates may only add normalized records or bump `content_hash`; `replace` is allowed for the same `id`; `pinned` blocks update without an explicit `--allow-pinned-bump` flag.
- Doctor adds: customer-mode dry-run (`doctor --profile=customer`) listing what would be excluded.
- Exit P3 when: customer-mode install of a mixed package set correctly excludes operator-only capabilities; pinned-bump guard fires in CI.

If any phase blows its 2-week cap, work stops and the orchestrator re-scopes — no rolling deadlines.

## Acceptance Criteria

1. `capability-declared.schema.json` and `capability-normalized.schema.json` exist; every hand-edited per-type registry file validates against the declared schema, and `capabilities.yml` + lock entries validate against the normalized schema. An injected invalid record causes `agentic-os install` to exit non-zero with a file:line pointer.
2. Per-type discriminator: a record with `type: rule` omitting `install.command`, `provides.tools`, and `requires.commands` passes declared-schema validation; a record with `type: mcp` omitting `provides.tools` fails declared-schema validation; **additionally**, a `type: rule` record with `provides.tools: []` present-but-empty FAILS declared-schema validation (`forbidden` means absent, not empty).
3. `agentic-os install --dry-run` is deterministic: running twice into separate output dirs at `./agentic-os.out/dry-run-A/` and `./agentic-os.out/dry-run-B/` produces byte-identical trees. CI asserts via `diff -r A B`.
4. `INVENTORY.md` lists every capability in `capabilities.yml`; an entry present in one but not the other causes doctor to fail.
5. `agentic-os doctor` exits 0 on a clean install of the current OS contents and exits non-zero with a numbered FAIL list otherwise.
6. A capability whose `install.command` is missing on PATH ends step 5 with derived `status = broken` in `capabilities.yml` and the lock file, and is excluded from generated harness adapters. The hand-edited per-type registry file for that capability is byte-for-byte unchanged after install.
7. `.codex/config.toml`, `CLAUDE.md`, and `AGENTS.md` are regenerable: re-running `install --dry-run` on an unchanged tree produces a zero-byte diff against the prior dry-run output.
8. Hand-curated content above the `<!-- AGENTIC-OS:REGISTRY-CURATED BELOW -->` sentinel survives a round-trip; the emitter aborts if the sentinel is absent.
9. `agentic-os.lock.json` contains a `manifest_hash` over the sorted entries; the hash changes iff any normalized record's content (including derived `status` or `doctor.last_run_status`) changes.
10. `AGENTIC_OS_PROFILE=customer` install refuses any capability with `customer_safe: false` and exits non-zero listing offenders.
11. An `additive_non_destructive` update that attempts to remove a capability fails before any file is written.
12. All three secret gates (structural schema rules, regex grep, entropy) run on every PR; injected fixtures violating any one gate fail the build.
13. **Disabled-record invariant**: a declared record with `status: disabled` produces a `capabilities.yml` entry and a lock entry where (a) `status: disabled`, (b) `source.content_hash` is ABSENT (verified by walking the nested object — no `content_hash` key under `source`), (c) the entire `doctor` object is ABSENT at the record's top level, (d) the record passes normalized-schema validation under the `status: disabled` branch, (e) no file is copied into the record's `install.target`, (f) no harness adapter mentions the record, and (g) the record IS listed in `INVENTORY.md` with a `(disabled)` annotation. Counter-fixtures (the schema must be two-sided): (h) a normalized record with `status: installed` and no `content_hash` under `source` FAILS validation, (i) a normalized record with `status: disabled` AND a `doctor` object containing `last_run_status: pass` FAILS validation (proves the disabled branch's `not: { required: ["doctor"] }` is correctly enforced at the right object depth — not as a dotted-path string).
14. **Adapter promotion atomicity (per-file + recovery)**:
    - (a) **Pre-promotion fault**: a fault injected after step 6 (staged adapters written) and before any `os.replace` in step 8a leaves live `.codex/config.toml`, `CLAUDE.md`, and `AGENTS.md` byte-identical to their pre-install snapshots (SHA256-compared).
    - (b) **Mid-promotion fault**: a fault injected AFTER the first `os.replace` (`.codex/config.toml` promoted) and BEFORE the second (`CLAUDE.md`) results in live `.codex/config.toml` carrying the new `AGENTIC-OS-GENERATION` line; `CLAUDE.md` and `AGENTS.md` still carrying the prior `AGENTIC-OS-GENERATION` line; the lock still containing the prior `manifest_hash`. `agentic-os doctor` then exits non-zero with a `mixed-generation` FAIL identifying which adapters disagree.
    - (c) **Post-promotion-pre-lock fault**: a fault after step 8a completes but before step 8b writes the lock leaves all three live adapters at the new `AGENTIC-OS-GENERATION` but the lock at the prior `manifest_hash`; doctor exits non-zero with a `mixed-generation` FAIL (live adapters disagree with lock).
    - (d) **Recovery**: running `agentic-os install --resume-promotion` after (a), (b), or (c) results in all three live adapters carrying the same `AGENTIC-OS-GENERATION` value, the lock's `manifest_hash` matching that value, and doctor exiting 0.

All validations live in `tests/` under the OS repo and run in the same CI job that builds the lock file.

## Risks

- **Adapter drift**: an operator hand-edits `.codex/config.toml` below the sentinel between installs. Mitigation: install starts by re-emitting and diffing; if non-zero, install warns + offers `--overwrite` or `--abort`; doctor flags drift even without an install.
- **Two schemas duplicate maintenance**: declared and normalized share the base via JSON Schema `$ref`; tests assert that any field added to declared is either inherited from base or explicitly overridden, and any normalized-only field (`content_hash`, derived `status`, `doctor` object) is not addable to declared. Drift between them fails CI.
- **Nested-schema encoding regressions**: the load-bearing disabled-record invariant requires nested `not: { required: ["content_hash"] }` on `source` and `not: { required: ["doctor"] }` at the record root — NOT dotted-path strings. A regression to dotted-path strings would silently fail open. Mitigation: AC13's counter-fixtures (h) and (i) specifically detect this regression. Schema reviews require explicit reference to the test that proves the encoding depth.
- **Two schemas duplicate maintenance**: covered above.
- **`status`-branched schema complexity**: the normalized schema's `oneOf` on `status` is the load-bearing piece for AC13. Mitigation: AC13 covers both positive (disabled passes) and counter (installed without content_hash fails; disabled with doctor present fails) — a one-sided schema mistake fails CI.
- **Disabled records bloat INVENTORY.md**: an operator who declares 50 capabilities and disables 30 of them sees noise. Mitigation: `INVENTORY.md` lists disabled records in a separate trailing section so the active surface stays scannable.
- **Mixed-generation adapter set after mid-promotion crash**: a crash between `os.replace` calls leaves the live adapters disagreeing. Mitigation: every adapter carries an `AGENTIC-OS-GENERATION` line; doctor's `mixed-generation` check compares each adapter's line against the lock's `manifest_hash`; `install --resume-promotion` reconverges. The window is narrow (microseconds between two `os.replace` calls) but real, and the spec treats it as a recoverable transient rather than pretending it cannot happen.
- **Staging-tree cleanup**: a crashed install leaves `.agentic-os.staging/` on disk. Mitigation: every install's startup phase deletes the staging tree before re-emitting; `doctor` reports a stale staging tree as a warning, not a failure. `install --resume-promotion` distinguishes a stale-but-matching staging tree (reusable) from a stale-and-stale staging tree (deleted).
- **Schema rigidity slows new capability types**: the per-type table is part of the spec, so adding a new type requires a spec amendment + schema bump (intentional friction). Mitigation: schema permits a typed `extra` map per capability type, validated by a per-type sub-schema; reviewed quarterly.
- **Determinism foot-guns**: Python dict ordering, YAML library defaults, locale-dependent sort. Mitigation: pin `ruamel.yaml` with explicit emitter settings, sort by `id` with a locale-independent comparator (`str.__lt__` on ASCII-only ids), fix `LANG=C.UTF-8` in CI.
- **Harness churn**: Codex or Claude change their config formats. Mitigation: each emitter is one file; the schema doesn't change, only the emitter.
- **MCP-not-startable masks deeper problems**: doctor's `mcp-starts` check launches a subprocess. A long-running hang would block install. Mitigation: 5s timeout per check, doctor records `timeout` as FAIL.
- **Customer-safe gating is binary**: granular per-tool gating may be needed later. Mitigation: `customer_safe` is a per-record boolean in v1; finer gating deferred to a follow-up spec.
- **Entropy gate false positives**: long hash-like IDs or `source.content_hash` could trigger; mitigated by the allowlist of key paths and a 4.5 bits/char threshold tuned on the current registry set. False-positive escalation procedure: add the offending key path to the allowlist only via PR review + spec changelog entry.

## What's NOT in v1

- Auto-generation of per-type registry files from filesystem scanning (registries are hand-edited in v1; a P4 may add a scaffolder).
- A package marketplace, remote fetch, or version-resolution algorithm; `agentic-os.package.json` only references local or already-cloned packages.
- Live capability discovery from running MCPs (the registry describes what's installed, not what a running server happens to expose).
- Per-tool customer-safety gating inside a capability (whole-record only).
- UI / web dashboard for the registry (CLI + `INVENTORY.md` only).
- Migrating `shared_factory/05-knowledge/skills/` away from being a compatibility mirror — left as an Open Decision in the rough idea, deferred to a follow-up spec.
- Choosing between Markdown-prompt commands vs. executable-shim commands — both are permitted by the schema (`type: command` with optional `install.command`); the decision is per-command, not OS-wide.
- Plugin packaging format choice (Codex-native vs. OS-native wrapper) — registries describe what exists; packaging format is out of scope.
- Auto-promotion of `customer_safe` from `false` to `true` via heuristic; only a human PR to the declared record may change `customer_safe`.
- True multi-file atomicity for adapter promotion (no per-generation symlinked directory; harnesses read fixed paths). Spec ships per-file atomicity + detection + `install --resume-promotion` recovery instead.
- Cross-host two-phase commit; the promotion phase covers same-filesystem files via `os.replace`, not cross-host coordination.
